## 0. Identity

**Glifo.** A glyph is the minimum unit of writing: the individual hand-drawn sign. It is exactly what the application reads, evaluates, and decides whether it understood.

The visual identity is built upon the **mythological griffin** (grifo) —eagle's head, lion's body— bringing the two core ideas of the product: sharp sight to read what is hard to read, and guardianship of the student's content.

> The glyph is the unit of writing. The griffin, its guardian.

The palette uses a **slate blue with a gold accent**, taken from the griffin's body and heraldic character, deliberately departing from the default tones generated by AI design tools. It is defined in **two complete modes, Night and Day**: both declare the same set of tokens and only change values, so no component needs to know the active mode.

Gold is the color of action and active states, not a brand decoration: if an element is gold, it can be touched. Brand identity rests on the logo.

The states of the confidence map —verified, repaired, escalated, uncertain— are coded with **color, formatting (underlines/fills), and explicit textual labels simultaneously**, ensuring the information remains accessible to users with color vision deficiencies. Full values are in `Glifo_Arquitectura_Estandares.md` §12.3.

## 1. The Problem

The cycle required by the brief —notes → knowledge → gaps against syllabus → directed study— depends entirely on a first step: that a photograph of a handwritten note is faithfully converted into structured content.

That first step is the fragile point of the project, and the brief itself identifies it as its main risk. The originally proposed mitigation is a screen where the student corrects the transcription before the AI compares it.

Our observation is that this mitigation does not scale. In courses like Calculus, Linear Algebra, or Physics, a real note contains integrals, matrices, subscripts, limits, and diagrams. A conventional text OCR does not recognize mathematical structure: it returns a character string unrelated to what was written. Asking the student to correct that by hand is equivalent to asking them to re-transcribe the entire page.

The result, if unresolved, is a reconstructed note that **looks** correct, and flashcards and quizzes generated from that error, without the student knowing.

---

## 2. Value Proposition

> Glifo digitizes handwritten notes —formulas and diagrams included— scaling processing only when necessary, and shows the student what it securely understood, what it had to repair, and what requires human review.

Three concrete commitments translated into architectural decisions:

| Commitment | Implementation |
|---|---|
| **Nothing is invented in silence** | Every fragment of the note carries a calculated, visible confidence level |
| **No photo is left unprocessed** | Automatic escalation to the next engine when the current one misses the threshold |
| **Cost is a design decision** | Each pipeline level has a known cost; the system records which level resolved each region |

---

## 3. Design Principles

1. **AI does not do everything.** Local, deterministic processing is maximized before invoking any model. Pre-processing, text OCR, segmentation, confidence calculation, coverage comparison, quiz grading, spaced repetition, and progress tracking do not use AI.
2. **Every AI call produces a persistent, reusable result.** AI is never used to recompute what has already been saved.
3. **Never one call per item.** Flashcard/quiz generation and region repair for the same page always travel in batches.
4. **Minimal context.** The syllabus is processed once into a persistent structure and is never sent entirely to a model again; only the relevant fragment is sent per call.
5. **Uncertainty is shown, not hidden.** If the system couldn't read something, it marks it; it does not hallucinate a completion.

## 6. Ingestion Engine: Branched Ladder

This is the core component of the project and the main architectural decision.

```text
  ┌─────────────────────────────────────────────────────────┐
  │ N0  LOCAL PRE-PROCESSING (OpenCV)                       │
  │     perspective correction · deskew · contrast          │
  │     quality metrics: blur, lighting, glare              │
  │     PAGE SEGMENTATION INTO REGIONS                      │
  │     └─ unrecoverable image → request new capture        │
  │        indicating the concrete reason                   │
  └───────────────────────────┬─────────────────────────────┘
                              ▼
  ┌─────────────────────────────────────────────────────────┐
  │ N1  LOCAL TEXT OCR (ML Kit)                             │
  │     executes on ALL regions                             │
  │     zero cost, offline                                  │
  └───────────────────────────┬─────────────────────────────┘
                              ▼
  ┌─────────────────────────────────────────────────────────┐
  │     REGION CLASSIFIER                                   │
  │     combines geometry (stroke density, aspect ratio)    │
  │     with N1's behavior on that region                   │
  └───┬─────────────────┬───────────────────┬───────────────┘
      │                 │                   │
   TEXT               MATH               DRAWING
   resolved             ▼                   │
   at N1     ┌──────────────────┐           │
             │ N1.5 MATH OCR    │           │
             │ → LaTeX + conf   │           │
             └────────┬─────────┘           │
                      │                     │
      ┌───────────────┴─────────────────────┘
      ▼
  ┌─────────────────────────────────────────────────────────┐
  │     VALIDATION GATES (deterministic, NO AI)             │
  │     · confidence below threshold          [device]      │
  │     · dictionary and course glossary check[device]      │
  │     · LaTeX fails to compile (JLaTeXMath) [backend]     │
  └───────────────────────────┬─────────────────────────────┘
                              ▼
  ┌─────────────────────────────────────────────────────────┐
  │ N2  SELECTIVE VISION REPAIR                             │
  │     only regions that failed gates, plus drawings,      │
  │     CROPPED and IN A SINGLE CALL per page               │
  └───────────────────────────┬─────────────────────────────┘
                              ▼
  ┌─────────────────────────────────────────────────────────┐
  │ N3  FULL PAGE VISION                                    │
  │     last resort, on student demand                      │
  └───────────────────────────┬─────────────────────────────┘
                              ▼
       Anything still unresolved is marked UNCERTAIN.
                  It is not inferred.
```

### Decisions and Rationale

**The classifier runs after N1, not before.** ML Kit is local and free, so it is better to run it on all regions and use its behavior as a classification signal: coherent text with high confidence indicates text; fragmented output with loose symbols indicates math; no output indicates drawing.

**Escalation is by region, not by page.** Only the crop that needs it is sent to a vision model, representing an order of magnitude less data than a full page.

**Escalating regions travel in a single call.** Unresolved formulas and drawings from the same page are batched, each with specific instructions.

**The original image is never discarded.** Every formula crop is preserved alongside the generated LaTeX. If the transcription is doubtful, the student sees the original.

**Where each gate runs.** Confidence scoring and the glossary check are pure functions over data the device already holds (`LocalCourseContext`), so they run on the device and work offline. **LaTeX validation runs on the backend**, immediately after N1.5, because N1.5 itself is a backend call — the LaTeX string is produced there and validating it in the same request avoids a round trip, and `LatexValidator` (JLaTeXMath) already sits in the `ai/validation` package. Being in that package does **not** make it an AI call: it is deterministic compilation, and it appears in the "processes not using AI" list in section 9. `JLaTeXMath-Android` on the client is a separate concern — it *renders* validated LaTeX for display, it does not validate it.

## 7. Evaluated Recognition Engines

| Engine | Type | Output | Cost | Status |
|---|---|---|---|---|
| **OpenCV** | Local | Normalized image + regions | None | Adopted — N0 |
| **ML Kit Text Recognition** | Local, on-device | Text | None | Adopted — N1 |
| **SimpleTex API** | External service | LaTeX + numeric confidence | Permanent free tier | Adopted — N1.5 |
| **Vision Model (LLM)** | External service | Text / LaTeX / description | Per token | Adopted — N2, N3 |
| **Mathpix** | External service | LaTeX | Paid | Discarded |
| **Tesseract** | Local | Text | None | Discarded: weak on handwriting |
| **ML Kit Digital Ink** | Local | Text | None | Discarded: requires screen strokes |
| **pix2tex / LaTeX-OCR** | Self-hosted | LaTeX | Own infrastructure | **Open Query — section 8** |

**Selection Criteria for N1.5.** Priority was given to engines providing a **numeric confidence signal derived from the model**, not self-reported. SimpleTex exposes a confidence field per response, allowing automatic routing decisions. 

**Design for Replacement.** N1.5 is defined as an interface (`MathOcrEngine`) with interchangeable implementations, making the concrete engine a configuration detail.

## 8. Professor Consultation: Self-hosted pix2tex

This decision is pending before freezing the architecture.

**The Proposal.** Deploy **pix2tex / LaTeX-OCR** as our own REST microservice and consume it from the backend as another `MathOcrEngine` implementation.

**Pros:** Total independence from external providers; student notes never leave our infrastructure; zero cost per call.
**Cons:** Introduces a second deployment; cold start latency on free hosting tiers is a direct risk for the live demo; lower reported accuracy on poorly lit photos compared to SimpleTex.

**Concrete Questions:**
1. Is an independent Python microservice acceptable for Lab 6, or does it contradict the monolithic requirement?
2. Does self-hosting our own model add evaluation value over consuming a free external service?
3. Is university infrastructure available to host it?
4. Considering cold starts, is the latency risk acceptable for the final defense?

**Team Stance.** Implement the external service route first, as it is immediately functional, and evaluate self-hosting as a later addition via the `MathOcrEngine` interface.

## 9. Artificial Intelligence Use Policy

| Identifier | Function | Trigger | Batching |
|---|---|---|---|
| **OCR-M** | Formula recognition → LaTeX | Region classified as math | Per region |
| **IA-00** | Selective vision repair | Regions failing validation gates | **One call per page** |
| **IA-01** | Note reconstruction to JSON | Once per note | Batch |
| **IA-02** | Flashcards and quizzes | Once per topic set | **Batch — never one call per item** |
| **IA-03** | On-demand concept explanation | Student request | Cached result |
| **IA-04** | Semantic coverage adjudication| Topics failing local pre-filter | Batch |

**Processes NOT using AI:** Image pre-processing, text OCR, segmentation, classification, deduplication, confidence scoring, LaTeX validation, coverage pre-filtering, progress delta, quiz grading, and spaced repetition.

Every AI output is persisted. The system does not reprocess already generated content.

**Count.** 16 core tables (access control, academic domain, ingestion, study) + 5 operations tables = **21**. Only the 16 core tables appear on the diagram defended in class; the annex is shown if asked. The reduction from 23 to 16 is justified in `Glifo_UML_Modeling.md` §4.2, and every merge rests on strict 1:1 cardinality.

### JSONB Usage Criteria

Applied selectively, not generalized.

**Criterion.** A column is JSONB when its structure is variable *and* no internal field is filtered or aggregated by a query. If either half fails, it is normalized.

| Uses JSONB | Justification |
|---|---|
| `note_pages.regions` | Number and shape of regions varies per page; normalizing adds no query value. |
| `note_pages.quality_metrics` | The metric set grows as N0 improves; read whole, never filtered. |
| `notes.content` | The structured note is a document tree. |
| `study_items.payload` | Structure differs completely by item kind (flashcard vs multiple choice). |
| `attempts.response` | Response format depends on the question type. |
| `sync_queue.payload` | Serialized outbox operation; opaque to the server until replayed. |
| `notifications.payload` | Payload shape depends on the notification kind. |
| `coverage_snapshots.summary` | Reporting-only freeze of a coverage state; never queried by field. |

Eight JSONB columns. The one that carries the most weight is `study_items.payload`: collapsing questions, options, and correct answers into it removed **four normalized tables** from the quiz model. A `CHECK` constraint keeps the `kind` discriminator and the payload honest.

| Does NOT use JSONB | Justification |
|---|---|
| `topic_coverage` | Filtered and aggregated constantly. |
| `syllabus_topics`, `enrollments` | Cardinal relationships with referential integrity. |
| `ai_calls` | Aggregated by level and cost; it is the ledger the defense depends on. |
| Access control block | Mandatory referential integrity. |

## 12. Local Storage and Synchronization

Corresponds to the team's applied research topic.

**Design**
- **Room** as a local read cache. All generated content is readable offline.
- **LocalCourseContext** synchronized to Room, containing the syllabus and glossary versions, enabling the pipeline and `ConfidenceScorer` to function 100% offline.
- **Capture Outbox.** Photos taken offline are queued locally. A `Note` is created locally in `DRAFT` status and transitions to `READY` on the server once pages sync.
- **Retries with Idempotency.** Every queue item carries a stable UUID. Partial synchronization failures do not result in duplicate records upon retry.
- **Targeted Push Notification** upon queue completion, routed exclusively to the physical `device_id` that uploaded the batch.
- **Perceptual Hash Deduplication:** An already processed page never consumes resources twice.

## 14. Technical Risks

| Risk | Mitigation |
|---|---|
| OpenCV Android integration size | Addressed early; only necessary modules included. |
| Region segmentation fails | Degrade to full-page processing (higher cost, keeps operating). |
| Threshold calibration | Adjust and measure against a fixed set of calibration photos. |
| Formula mistranscription | Original crop is always shown next to the LaTeX. |
| Math OCR latency/downtime | `MathOcrEngine` is swappable, falls back to vision model. |
| Region classification error | It escalates anyway once confidence drops. Costs latency, not correctness. |
| Network failure during sync | Exponential backoff retries with idempotent identifiers. |
